## 0. この文書の目的

4人が別々にAIに質問すると、AIごとに違うテーブル名・違う関数名・違うディレクトリ構成を提案してきます。その結果、各自のコードは単体では動くのに、合流させた瞬間に動かなくなります。**2週間しかない本プロジェクトで最も起こりやすい事故がこれです。**

これを防ぐため、**4人全員が同じ前提文をAIに渡す**ことにします。以下の「2. 共通前提テンプレ」を、AIに質問するたびに毎回コピーして貼り付けてください。毎回です。新しいチャットを開いたときだけではありません。

### 1.3 データベースの定義

```sql
CREATE TABLE IF NOT EXISTS records (
    id       INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id  TEXT    NOT NULL,              -- 利用者の識別子（1.4参照）
    date     TEXT    NOT NULL,              -- 記録日 'YYYY-MM-DD'
    category TEXT    NOT NULL,              -- カテゴリキー（1.4参照）
    minutes  INTEGER NOT NULL,              -- 分。30の倍数（0.5時間 = 30分）
    UNIQUE (user_id, date, category)
);
```

**決めた理由**

- **1行 = 1人の1日の1カテゴリ**。8カテゴリ分を8行で持ちます。カテゴリごとに列を作る形（`sleep` 列、`school` 列…）にすると、カテゴリを増やすたびにテーブル定義を変える必要が出るためです。
- **時間は「分」の整数で持つ**。小数（0.5時間）で持つと計算誤差が出ます。0.5時間 = 30分、7時間 = 420分。画面に出すときだけ `minutes / 60` で時間に直します。
- **`UNIQUE (user_id, date, category)`** を付けてあります。これによって「同じ日に2回保存された場合」の扱いが決まります → 1.5参照。

### 1.4 カテゴリ定義

**この定義は `categories.py` に1か所だけ書き、全員がそれをimportして使います。** 各自が自分のファイルにカテゴリ名を直接書くと、表記揺れ（「スマホ」と「スマホ・動画・SNS」）でデータが分裂します。

```python
# categories.py  ... オカダが作成。変更は4人の合意が必要

# 入力画面に並ぶ順に定義する
CATEGORIES = [
    ("sleep",   "睡眠"),
    ("school",  "学校"),
    ("study",   "勉強・自習"),
    ("life",    "生活"),
    ("move",    "移動"),
    ("phone",   "スマホ・動画・SNS"),
    ("fun",     "娯楽"),
]

# 「その他」は利用者が入力しない。サーバー側で残り時間を自動計上する
OTHER = ("other", "その他")

# 表示名を引くための辞書
LABELS = dict(CATEGORIES + [OTHER])
```

DBに入れるのは英字のキー（`sleep`）、画面に出すのは日本語（`睡眠`）です。DBに日本語を入れない理由は、文字化けや打ち間違いの事故を避けるためです。

利用者の識別子（`user_id`）も同様に、`abe` / `oishi` / `okada` / `nakamura` の4つを `categories.py` と同じ要領で1か所に定義します。

### 1.5 動作の取り決め

| 項目                             | 決定内容                                                                                                            |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 記録のタイミング                 | 1日1回、就寝前にその日1分をまとめて入力                                                                             |
| 睡眠の日付                       | **前の晩に寝た分**を当日の記録とする（10/16の記録 = 10/15夜〜10/16朝の睡眠）                                  |
| 入力の刻み                       | 0.5時間（30分）単位。選択肢は 0.0 〜 24.0                                                                           |
| 同じ日に2回保存されたとき        | **上書きする**（後から入力した内容を正とする）。`INSERT ... ON CONFLICT ... DO UPDATE` を使う             |
| 合計が24時間に満たないとき       | 残り時間を「その他」として**サーバー側で**自動計上する                                                        |
| 合計が24時間を超えたとき         | **保存せず入力画面に戻し、エラーを表示する**。超えたまま保存させない                                          |
| 合計の計算をどこで行うか         | **サーバー側（Python）**。JavaScriptを使わないため、ブラウザ上でリアルタイムに合計を出すことはできない        |

**補足（重要）**

JavaScriptを使わない方針により、入力中に合計が画面上で自動更新されることはありません。利用者が「保存」を押した後、サーバーが合計を検証し、

- 24時間ちょうど、または24時間未満 → 「その他」に残りを入れて保存し、一覧画面へ
- 24時間超 → 保存せず、入力画面を再表示して「合計が24.0時間を超えています（現在 25.5 時間）」と表示

という動きになります。この挙動は企画書2章・8章の記述（「画面側で自動計算」）と食い違っているため、企画書側を修正します。

## 3. 担当ごとの「最初の1問」

環境構築（10/18）が終わったら、各自これをAIに投げるところから始めてください。上のテンプレを貼った後に続けて書きます。

### ナカムラさん（入力画面）

> 上の前提で、カテゴリ別の合計時間を入力するフォーム画面を作りたいです。`templates/input.html` と、それを表示する `app.py` のルートを教えてください。7項目それぞれに 0.0〜24.0 を0.5刻みで選ぶプルダウンを置き、送信先は `POST /record` です。JavaScriptが使えないので、合計の検証はサーバー側で行う前提です。フォームの `name` 属性をカテゴリの英字キーに対応させる方法と、送られてきた値を `app.py` で受け取る書き方を教えてください。

### アベさん（データ保存）

> 上の前提で、`db.py` に次の3つの関数を作りたいです。(1) DBとテーブルを初期化する関数、(2) 1人の1日分（8カテゴリ）を保存する関数、(3) 指定した利用者と期間の記録を取り出す関数。まず関数名・引数・戻り値の形（辞書かタプルか）を提案してください。コードはその合意ができてから書きたいです。同じ日に2回保存されたときに上書きする書き方（`ON CONFLICT`）も教えてください。

### オオイシさん（可視化・通知）

> 上の前提で、`records` テーブルから1週間分のデータを取り出し、カテゴリ別の時間配分を円グラフにしたいです。JavaScriptが使えないので、matplotlibで画像ファイルを生成して `static/graphs/` に保存し、HTMLの `img` タグで表示する方法を教えてください。あわせて、matplotlibで日本語のラベルが文字化けする問題（豆腐になる）の対処法を、Windows環境を前提に教えてください。

### オカダ（デプロイ・運用）

> 上の前提で、EC2上でこのFlaskアプリを常時稼働させたいです。Flaskの開発用サーバーをそのまま使ってはいけない理由から説明し、gunicorn + systemd + nginx の構成を、各要素が何をしているか理解できるように1ステップずつ教えてください。

### 文書（全員）

> 自分が担当した〇〇について、設計書に載せる説明文を書きたいです。いきなり書き始めず、**先に私への質問を出してください。** どんな情報をあなたに渡す必要があるかを知りたいです。

最後の「先に質問してください」という形は、文書作成では特に有効です。いきなり書かせると、AIが想像で埋めた**実装と違う嘘の仕様書**ができあがります。

## 4. AIに聞くときの3つのルール

### ルール1 — 「動いたコード」ではなく「説明」を要求する

コードを受け取ったら、必ずこう聞き返してください。

> このコードの〇行目は何をしていますか。初めて見る書き方なので、文法から説明してください。

企画書12章で、**全モジュールについて作者以外の1名が処理内容を口頭で説明できること**を各段階の完了条件にしています。説明できないコードは、レビューを通りません。就職活動のポートフォリオとして見せる以上、説明できないコードは載せられません。

### ルール2 — エラーは加工せず全文を貼る

「エラーが出ました」だけだと、AIは推測で答えます。これが一番時間を溶かします。

> 以下のエラーが出ました。原因の候補を挙げて、確認する順番を教えてください。
> （ターミナルに出た赤い文字を最初から最後まで全部コピーして貼る）

一部を省略したり、要約したりしないでください。最後の1行だけでは原因が特定できません。

### ルール3 — 担当外に手を出す提案は止める

AIは平気で「`app.py` をこう書き換えてください」と言ってきます。自分の担当外のファイルです。そのときはこう聞き返してください。

> この変更は他の担当者のファイルに影響しますか。影響する場合、私の担当範囲内だけで解決する方法はありますか。

影響するなら、**実装する前に4人で共有**してください。ここを守らないと、合流時に「同じファイルを2人が別々に書き換えていた」という状態になります。

## 5. やってはいけないこと

| やってはいけないこと                                     | 理由                                                                   |
| -------------------------------------------------------- | ---------------------------------------------------------------------- |
| `.env` をGitにコミットする                             | Discordのトークンが公開リポジトリに残ります。`.gitignore` 済みです |
| `app.db` をGitにコミットする                           | 各自の記録が混ざり、コミットのたびに衝突します                         |
| テーブル定義・カテゴリ名を自分の判断で変える             | 他の3人のコードが動かなくなります                                      |
| JavaScriptを使う（AIが提案してきても）                   | 方針として決定済みです。提案されたら断ってください                     |
| 意味が分からないコードをそのまま貼り付けて「動いた」とする | レビューを通らず、企画書の完了条件を満たしません                       |
| `main` ブランチに直接pushする                          | 作業は自分のブランチで行います（手順書の7章参照）                      |

## 6. 困ったときの連絡先

環境構築・サーバー・Git まわりで詰まった場合は、各自でAIと格闘せずに**オカダに連絡してください。** 3人の手元は「Pythonを書いて動かす」ところまでに絞るのが、2週間で終わらせるための前提です。

Pythonのコードそのものや、自分の担当範囲の設計についてはAIと詰めて構いません。その結果は水曜・日曜の相談で共有してください。
