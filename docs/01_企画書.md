## 1. プロジェクト概要

| 項目                           | 内容                                                                                                                                           |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| プロジェクト名（仮）           | 生活習慣改善プログラム                                                                                                                         |
| 一行サマリ                     | 学生の「何に時間を使ったか分からない」という状態を、PC・スマホから1日の時間配分を記録し可視化することで解決する                                |

## 2. 用語定義

| 用語         | 定義                                                                                                                                                               |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 時間配分     | 1日24時間を、カテゴリ別に何時間使ったかに分けたもの                                                                                                                |
| 記録単位     | 0.5時間（30分）。カテゴリごとの合計時間を0.5時間刻みで入力する                                                                                                     |
| 記録日       | 入力の対象となる日付。就寝前に当日分を入力する。**睡眠はその日の朝までの睡眠（前の晩に寝た分）を当日の記録として扱う**                                             |
| カテゴリ     | 記録時に時間数を入力する項目。暫定一覧は9章                                                                                                                        |
| 無駄な時間   | 本人が事後に「別のことに使いたかった」と判断した時間。**アプリ側では判定しない**。アプリの役割は時間配分を事実として見せることまでで、良し悪しの判断は利用者が行う |
| 記録漏れ     | 入力した合計が24時間に満たない分。自動的に「その他」へ計上される                                                                                                   |
| 第1〜第3段階 | 開発の段階。定義は11章                                                                                                                                             |

**記録方式**: 時刻ごとに何をしていたかを記録するのではなく、カテゴリごとの合計時間を入力する方式を採る。入力画面は次の形になる。

```
睡眠               [ 7.0 時間 ▼]
学校               [ 6.5 時間 ▼]
勉強・自習         [ 1.5 時間 ▼]
生活               [ 2.0 時間 ▼]
移動               [ 1.0 時間 ▼]
スマホ・動画・SNS  [ 2.5 時間 ▼]
娯楽               [ 1.5 時間 ▼]
その他             （入力欄なし）     ← 送信後にサーバー側で自動計上
                   ［ 保存 ］         ← 押した後にサーバー側で合計を検証
```

入力は7項目（「その他」は自動計上）で完結する。選択肢は0.5時間刻みで0〜24時間。**合計の検証と「その他」の算出は、送信後にサーバー側（Python）で行う。** JavaScriptを使わない方針のため、入力中にブラウザ上で合計が自動更新されることはない（8章）。

この方式を採ることで**時刻の情報は記録されない**。本アプリが知りたいのは「何にどのくらいの時間を割いているか」であり、「何時に何をしていたか」ではないため、時刻を捨てて入力の手数を優先する（6章・15章の決定）。

**睡眠の日付の扱い**: 就寝前に入力するため、その日の記録に入れる睡眠は「これから寝る分」ではなく「その日の朝まで寝ていた分（前の晩の睡眠）」とする。10月16日の記録であれば、10月15日の夜から10月16日の朝までの睡眠を入力する。4人で入れ方が分かれるとデータが揃わないため、入力画面にもこの旨を表示する。

「無駄な時間」は人によって基準が異なるため、アプリが自動判定する機能は持たせない（10章参照）。

## 3. 解決したい課題

| No    | 場面         | 困りごと                                                      | 今どうしているか                       | 重要度                      |
| ----- | ------------ | ------------------------------------------------------------- | -------------------------------------- | --------------------------- |
| 課題1 | 記録するとき | 記録が面倒で続かず、途中でやめてしまう                        | 手書きやアプリを試したが定着しなかった | **最重要**                  |
| 課題2 | 帰宅後       | 携帯を見ていたら夜になっている                                | 対策できていない                       | 高（1日の総量のみ対象）     |
| 課題3 | 寝る前       | 動画やSNSを見てしまい、就寝時間が後ろ倒しになる               | 対策できていない                       | 高（第1段階では測定対象外） |
| 課題4 | 日曜の夜     | 1週間を振り返っても何をしたか思い出せず、翌週の計画が立たない | 対策できていない                       | 高                          |
| 課題5 | 通学・移動中 | まとまった時間があるのに、何に使ったか覚えていない            | 対策できていない                       | 中（第1段階では測定対象外） |

課題1を最重要とする。記録が続かない限り課題2〜5はデータが揃わず判断できないため、他のすべての前提になる。したがって実装の優先順位も「入力の軽さ」から決める。

本プログラムの打ち手は次の3つである。

1. 記録の負担を最小化する（カテゴリ別の合計時間を選択式で入力・0.5時間刻み）→ 課題1
2. 記録した内容をその場で可視化する（グラフ表示）→ 課題2・4
3. 記録を促す仕組みを日常の導線上に置く（Discord通知）→ 課題1・3

**時刻を記録しないことによる課題への影響**: 2章のとおり時刻を記録しないため、課題2・3・5は扱える範囲が限られる。それぞれ次のとおりとする。

| 課題  | 扱える範囲                                         | 扱えない範囲                                         |
| ----- | -------------------------------------------------- | ---------------------------------------------------- |
| 課題2 | 1日のスマホ・動画・SNSの**総量**に気づくところまで | その時間が帰宅後に集中していたかどうか               |
| 課題3 | —（第1段階では測定対象外）                         | 就寝時刻が何時だったか、後ろ倒しになっているかどうか |
| 課題5 | 移動に使った**総量**に気づくところまで             | 移動中の時間を何に使ったか                           |

課題3・課題5は第1段階では**測定対象外**とし、課題として残したうえで改善の確認は行わない。課題3に対する打ち手（就寝前のDiscordリマインド）は実施するが、効果を数値で確認する手段は持たない。課題2は総量の可視化までを対象とし、時間帯の偏りは扱わない。時刻の記録を再検討するのは、第1段階の運用後に必要性が確認された場合とする。

## 4. ターゲットと利用シーン

| 項目                 | 内容                                                                         |
| -------------------- | ---------------------------------------------------------------------------- |
| 主な利用者           | 開発者4名（アベ・オオイシ・オカダ・ナカムラ）                                |
| 想定する試用者       | 第3段階で開発者以外2〜3名                                                    |
| 入力するタイミング   | 就寝前（その日1日分をまとめて記録）。Discordのリマインドは**毎日21時**に送る |
| 入力の頻度           | 1日1回                                                                       |
| 入力にかけてよい時間 | 1回あたり2分以内（上限）                                                     |
| 使うデバイス         | PC・スマートフォン（ブラウザ）                                               |
| 振り返るタイミング   | その日の入力直後、および週末                                                 |

睡眠時間は起床時刻がほぼ一定であるため、就寝前の時点で当日分をおおよその値として申告できる。したがって起床時の入力は行わず、1日1回の記録に統一する。記録する睡眠は前の晩に寝た分である（2章）。

リマインドを21時としたのは、就寝前に記録する運用において、記録して就寝するまでに余裕を持たせるためである。21時の時点で未入力の利用者にDiscordから通知する。

**未検証の前提**: 入力は7項目であり、操作回数の面では課題1をほぼ解消できる見込みである。残る前提は**申告値の精度**である。本方式は「今日スマホを何時間見たか」を記憶から申告する形になるため、過小申告・過大申告が生じうる。特にスマホ・動画・SNSの時間は少なく申告されやすい。これに対し、**スマホ・動画・SNSの時間はiOS/Androidのスクリーンタイムの数値を確認してから入力する運用ルール**を設ける（9章）。他カテゴリの申告精度については、第1段階の運用で「その他」の比率を見て判断する（13章参照）。

## 6. 形態の選定

| 判断軸                      | Discord Bot単体                          | Flask Webアプリ単体                | Web＋Discord併用                      | 重視度 |
| --------------------------- | ---------------------------------------- | ---------------------------------- | ------------------------------------- | ------ |
| 入力の手軽さ                | ○ アプリ内で完結                         | △ ブラウザを開く手間               | △ 入力はブラウザ                      | ◎      |
| 7項目を一度に入力する操作性 | △ 対話形式では1項目ずつになる            | ◎ 1画面にまとめられる              | ◎ 1画面にまとめられる                 | ○      |
| 記録の見返しやすさ          | × 対話のログが流れ、過去の記録が埋もれる | ◎ 一覧画面で日付を指定して見られる | ◎ 一覧画面で日付を指定して見られる    | ◎      |
| 選択式UIの作りやすさ        | ○ ボタンが標準機能                       | △ HTMLフォームを自作               | △ HTMLフォームを自作                  | ○      |
| グラフ可視化の自由度        | △ 画像を生成して貼る                     | ○ 画像を生成して表示               | ○ 同じ画像を画面とDiscordに使える     | ◎      |
| 過去データの閲覧・編集      | × 不得意                                 | ◎ 得意                             | ◎ 得意                                | ◎      |
| 記録を促す仕組み            | ◎ 通知が標準機能                         | × 自分で見に行くしかない           | ◎ Discordから通知                     | ◎      |
| 複数人での利用              | ○ 同じサーバーにいれば完結               | △ 利用者識別が必要                 | △ 利用者識別が必要                    | △      |
| 学習として得たいもの        | discord.pyの扱い                         | Web全体（HTTP・DB・画面）          | Web全体＋デプロイ・常時稼働・定期実行 | ◎      |

**決定**: Web＋Discord併用。入力と閲覧はFlask Webアプリ、リマインドと週次サマリの通知はDiscordが担う。

**決めた理由**

1. **記録を後から見返せるのはWebだけである。** Discord Botの対話形式では、記録がチャンネルのログとして流れていく。日々の記録が他の発言と混ざって蓄積するため、過去の記録を探す・読み返す・修正するという操作が成立しない。前回作成したDiscord Botを実際に運用して、この点が最も使いにくかった。本アプリは記録を溜めて振り返ることが目的であり（課題4）、記録が埋もれる形態は選べない。
2. 入力の操作回数という観点では、7項目であればBotの対話形式でも成立しうる。したがって本決定の根拠は操作回数ではなく、上記の見返しやすさ、およびグラフ可視化の自由度（課題2・4）に置く。
3. Web単体では「記録を促す仕組み」が作れず、課題1・3に手が届かない。通知だけをDiscordに持たせることで、入力の操作性と継続の仕組みを両立できる。
4. 学習目的との相性が最も良い。常時稼働させるサーバー、デプロイ、定期実行を扱う構成になり、目指しているインフラ・クラウド系の分野と重なる経験が得られる。

## 9. 記録カテゴリ（暫定）

入力画面に並ぶ項目。**少ない数で始め、データが溜まって傾向が見えてから分割する**方針とする。カテゴリを増やすとそのまま入力項目の数が増え、課題1に反する。

| No  | カテゴリ          | 含むもの                                                                                                       |
| --- | ----------------- | -------------------------------------------------------------------------------------------------------------- |
| 1   | 睡眠              | 就寝から起床まで。仮眠を含む。**前の晩に寝た分を当日の記録とする**（2章）                                      |
| 2   | 学校              | 授業、および校内で過ごした時間                                                                                 |
| 3   | 勉強・自習        | 校外での学習、資格勉強、本プロジェクトの作業                                                                   |
| 4   | 生活              | 食事、入浴、身支度、家事                                                                                       |
| 5   | 移動              | 通学、外出時の移動                                                                                             |
| 6   | スマホ・動画・SNS | 目的を決めずに見ていた時間                                                                                     |
| 7   | 娯楽              | ゲーム、友人との外出など、意図して使った余暇                                                                   |
| 8   | その他            | 上記に当てはまらない時間。**合計が24時間に満たない分を自動的にここへ計上する**。利用者は入力しない（自動計算） |

**「その他」の前提**: 4人の生活においてカテゴリ1〜7で1日の活動はすべて説明できるため、**思い出せずに入力が漏れる時間は発生しない前提とする**。したがって「その他」に計上される時間は、カテゴリ1〜7のどれにも当てはまらない活動そのものを指す。

この前提は運用で検証する。「その他」の比率が無視できない水準まで上がった場合、それは前提が崩れたサイン（カテゴリが生活の実態を覆えていない、または入力漏れが起きている）として扱い、カテゴリ定義を見直す（12章・13章）。

アルバイトは独立したカテゴリにしない。現時点で4人の中にアルバイトをしている者がいないため、該当する時間が発生した場合は「その他」に含める。記録が溜まって「その他」の比率が大きくなった段階で分割を検討する。

カテゴリ6と7を分けているのは、同じスマホの利用でも「目的なく見ていた時間」と「意図して楽しんだ時間」を区別したいためである。この区別が自己判断に委ねられる点は承知の上で、2章の「無駄な時間」の定義に沿って利用者側が判断する。

**入力の運用ルール（スクリーンタイムの参照）**

カテゴリ6「スマホ・動画・SNS」については、**iOS／Androidのスクリーンタイム（デジタルウェルビーイング）の数値を確認してから入力する**。記憶だけに頼ると、このカテゴリは実態より少なく申告されやすいためである。本アプリは手入力を前提とし、スクリーンタイムの自動連携は行わない（10章「ウェアラブル連携・自動計測」と同じ理由）。利用者が数値を目視で確認し、その値を参考に入力するという運用で対応する。

なおスクリーンタイムの合計には、カテゴリ7「娯楽」に該当するスマホ利用（意図して遊んだゲームなど）も含まれる。したがってスクリーンタイムの合計値をそのまま入力するのではなく、**目的を決めずに見ていた分**を利用者が切り分けて入力する。この切り分けは自己判断に委ねる。

### 本番環境の構成（第2段階）

第1段階は各自のPCでFlaskの開発サーバーを起動する。第2段階は、誰のPCも起動していない時間帯（21時のリマインド、週次サマリの投稿）にも動き続ける必要があるため、次の構成をとる。

| 項目         | 決定内容                                          | 役割                                                                         |
| ------------ | ------------------------------------------------- | ---------------------------------------------------------------------------- |
| サーバー     | AWS EC2 インスタンス1台                           | アプリを常時稼働させる土台。費用は初期クレジットの範囲内に収める             |
| アプリの起動 | gunicorn（WSGIサーバー）                          | Flaskの開発サーバーは本番用ではないため置き換える                            |
| プロセス管理 | systemd                                           | サーバーを再起動してもアプリが自動で立ち上がる状態にする（＝常時稼働の実体） |
| 公開         | nginx（リバースプロキシ）＋ 独自ドメイン ＋ HTTPS | スマートフォンのブラウザから入力するため、ドメインとHTTPSで扱いやすくする    |
| 定期実行     | cron                                              | 毎日21時のリマインド、および週次サマリの投稿スクリプトを起動する             |
| データベース | SQLite（サーバー上のファイル）                    | 記録の保存先                                                                 |
| バックアップ | cronで1日1回コピー                                | DBが失われると検証そのものが成立しないため                                   |
| 更新の反映   | Git（GitHubからgit pullしてサービス再起動）       | 手順を文書に残し、誰でも同じ操作で反映できるようにする                       |

このうち「プロセス管理」「定期実行」「バックアップ」「更新の反映」は、12章の学習指標に挙げた**常時稼働・デプロイ・定期実行**そのものにあたる。構成を決めた理由を自分の言葉で説明できる状態を、第2段階の完了条件とする。

**【要確認】** バックアップの保存先（同一インスタンス内の別ディレクトリか、S3などの外部か）は設計時に決める。同一インスタンス内に置く場合、インスタンスごと失われたときには復旧できない点を承知の上で選ぶ。
